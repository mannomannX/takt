# M11 — Einbettung: Takt als Baustein in Rust- und C-Projekten

Stand: 2026-10-02, überarbeitet am selben Tag (Portvertrag statt
einzelner Bindungen, beliebige RTOS und Betrieb ohne RTOS neben fremdem
Code, Entwicklererfahrung). Bezug: `plan/plan.md` (Reihenfolge nach
M10), `plan/m10.md` (2.5: die Bindung mit Funkstack ist Nachzug; 2.12:
Speicherschutz; Schritt 11c: Treiber-Crates in Rust; Schritt 34: die
Stromzähler in zwei Rahmen), `plan/m9.md` (Knotenbuild, folgt auf M11),
`plan/cert.md` (TCB), `plan/definition.md` (4.2, 8.10, 9.9, 11.1, 11.2,
11.3, 11.5, 12.1, 12.3, 12.6, 12.7, 12.8, 13.8).

Bis heute besitzt ein Takt-Programm den Chip: Das Bring-up eines Boards
erzeugt den Rahmen, bindet Treiber, Schleife und Telemetrie und ist das
ganze Abbild. Wer Takt in ein eigenes Projekt holen will — eine
Zustandsmaschine mit korrekt gerundeter Mathematik in einer
Rust-Firmware, ein Regler neben einem Funkstack, ein Baustein in einer
Zephyr-Anwendung, ein Linux-Dienst —, findet keinen Weg, der nicht durch
die Testcrates dieses Repositorys führt.

M11 macht aus dem erzeugten Code einen Baustein, der **in jeder
Umgebung** läuft: auf einem Kern allein, neben fremdem Code ohne RTOS,
unter jedem RTOS, unter Linux und auf dem PC im Test. Das gelingt nicht
über eine Liste von Bindungen, sondern über einen kleinen Vertrag: Takt
wartet nie selbst, sondern sagt, wann es wieder gerufen werden will, und
was ein Wirt dafür stellen muss, sind eine Uhr, ein Kontext für den
Schritt und — nur wenn das Programm Jobs hat — ein Kontext darunter
(2.3). Jede Umgebung, die das kann, trägt Takt; die mitgelieferten Ports
sind Bequemlichkeit, nicht Voraussetzung, und eine Portprüfung belegt
jeden, auch einen fremden.

Gemessen wird M11 an zwei Dingen: an den Garantien (der Trace jeder
Einbettung gleicht dem Interpreter, der Speicher ist beim Übersetzen
bekannt, nichts fällt still auf einen Vorgabewert zurück) und an der
Entwicklererfahrung (ein Befehl zum ersten laufenden Projekt, Fehler
beim Bauen statt im Lauf, Tests auf dem PC gegen den Interpreter ohne
eigene Arbeit; 2.9).

Die Semantik ändert sich nicht. Die Referenz ändert sich dort, wo sie
voraussetzt, dass das Programm den Chip besitzt, und bekommt einen
Abschnitt für die Einbettung (Abschnitt 7). Jede Entscheidung in
Abschnitt 2 nennt die erwogenen Optionen und gibt der den Vorzug, die
auch in fünf Jahren noch trägt.

---

## 0. Umfang und Abnahme

M11 ist fertig, wenn ein fremdes Projekt ein Takt-Programm mit einem
Aufruf im Bauskript (Rust) oder einer Zeile im CMake-Projekt (C, Zephyr,
ESP-IDF) bindet, der veränderliche Speicher des Programms vollständig
vom Wirt gestellt und beim Übersetzen bekannt ist, jeder mitgelieferte
Port die Portprüfung besteht und der Trace jeder Einbettung dem
Interpreter gleicht.

| Abnahme | Nachweis |
|---|---|
| Eine Schnittstelle | die Bring-ups beider Boards und `takt-bringup-host` binden ihre Programme über `takt-embed`; Board-Suiten F401 und C6 ohne Abweichung; beide Boards neu kalibriert |
| Speicher vom Wirt, Größe bekannt | `ARENA_BYTES`, `ARENA_ALIGN`, `TICK_STACK_BYTES`, `JOB_STACK_BYTES` als Konstanten in Rust und C; `takt check-image` findet im gebundenen Abbild keinen veränderlichen Takt-Speicher außerhalb der Arenen |
| Ohne RTOS neben fremdem Code | Interruptform in Rust und C auf beiden Boards neben einer fremden Hauptschleife, die ihre eigene Arbeit tut; Pollform auf dem F401; Traces gleich dem Interpreter, `drift` im Bericht |
| Unter RTOS | Zephyr auf beiden Boards, FreeRTOS auf dem F401, ESP-IDF mit aktivem Funk und NVS-Schreibvorgängen auf dem C6, Embassy auf beiden Boards, RTIC auf dem F401; die generischen Ports CMSIS-RTOS2 (unter Zephyr) und POSIX (Linux); jeder besteht `takt port-test` |
| Mehrere Programme, mehrere Instanzen | zwei Programme mit verschiedenen Ticks auf dem F401 ohne RTOS und unter Zephyr, beide Traces gleich dem Interpreter; auf dem Wirt acht Instanzen in parallelen `cargo test`-Fäden |
| Rechnen bleibt bitgleich | ein Wirt, der Rundungsmodus oder Flush-to-Zero verstellt, und eine fremde Aufgabe, die gleichzeitig mit der FPU rechnet, ändern keinen Trace (x86-64, F401) |
| Treiber typisiert | ein fehlender oder falsch benannter Treiber bricht das Übersetzen (Rust) oder den Link (C); kein schwaches Symbol mehr im Rahmen |
| Abbild geprüft | `takt check-image` auf jedem Beispielabbild: ABI-Version und Logik-Hash, Arena und Stacks wie im Manifest, Tick-Pfad RAM-resident (`xip_flash`) |
| Entwicklererfahrung | `takt new --embed <form>` erzeugt für jede Form ein Projekt, das ohne Änderung baut und seinen Test auf dem PC besteht (in der CI); jede Vertragsverletzung, die der Bau erkennen kann, ist ein Baufehler mit Vorschlag (Liste in 2.9) |
| Inventur | die neuen Zeilen in `plan/features.csv` `fertig`, die Referenzstellen aus Abschnitt 7 nachgezogen |

### 0.2 Der Weg eines fremden Projekts (Ziel)

So soll es sich nach M11 anfühlen; die Namen sind Entwurf, die
Schritte 7 und 8 legen sie fest. Der Anfang ist ein Befehl:

```
takt new --embed rust-isr valve     # oder: rust-embassy, rust-rtic, c-isr, zephyr, freertos, esp-idf, cmsis-rtos2, posix, linux
```

Er legt ein Projekt aus der passenden Vorlage an: ein Takt-Programm, eine
`.hw`-Datei mit der Zielklasse, Treiber-Stummel, den Port und einen Test,
der auf dem PC gegen den Interpreter läuft. Ein Rust-Projekt bindet im
Bauskript:

```rust
// build.rs
fn main() {
    takt_embed::Program::new("takt/valve.takt")
        .hardware("takt/board.hw") // Zielklasse, Budget, Kalibrierung
        .drivers("crate::io::Board") // erfuellt `valve::Drivers`
        .build();
}
```

Ohne RTOS, neben einer eigenen Hauptschleife, ruft die Timer-ISR den
Kern und stellt den Timer auf die Frist, die er nennt; Jobs rechnen in
einem Interrupt niedrigster Priorität, und die Hauptschleife bleibt
unberührt:

```c
void TIM2_IRQHandler(void) {
    timer_ack();
    valve_next n = valve_service(&valve, clock_now_ns());
    timer_arm(n.deadline_ns);
    if (n.jobs) {
        NVIC_SetPendingIRQ(TAKT_JOBS_IRQn);
    }
}
```

Unter Zephyr ist Takt ein Modul; die Anwendung schreibt eine Zeile in
ihre `CMakeLists.txt` (`takt_add_program(valve SOURCE takt/valve.takt
HARDWARE takt/board.hw)`), schaltet `CONFIG_TAKT=y` und bekommt Faden,
Stack, Timer und Partition vom Port. Unter jedem anderen RTOS ist es
derselbe Kern mit einem Port von rund vierzig Zeilen (2.5).

Was der Entwickler über seine Hardware wissen muss, steht in der
`.hw`-Datei: die Zielklasse (12.8), den Anteil an RAM und Flash, den er
Takt gibt, und — einmal je Board — die Kalibrierung, die `takt bench`
über denselben Bausteinweg misst (2.12). Die Ergebnisse der Rechnung
hängen nicht am Chip (4.2); am Chip hängt, wie schnell sie kommen, und
das sagt die Kostentabelle, bevor das Programm läuft.

## 1. Befunde, die die Reihenfolge bestimmen

**1.1 Der Rahmen ist Produkt, liegt aber im Testcrate.** Was ein fremdes
Projekt binden müsste, erzeugt `takt-conformance` — das Crate, das den
Codegen gegen den Interpreter prüft. Ein Prüfer, der zugleich das
Geprüfte herstellt, ist für die Zertifizierung (13.4) die falsche
Ordnung, und jede Änderung am Rahmen landet heute im Testcrate. Darum
zieht der Generator zuerst um, ohne Verhaltensänderung (Schritt 2); alle
folgenden Änderungen stehen dann am richtigen Ort.

**1.2 Der erzeugte Code ist schon zeigerbasiert.** Die Maschinenfunktionen
bekommen Zustand, Abbild, Parameter und Latch als Zeiger; statisch sind
nur der Rahmen und drei Fault-Globale. Der Speicher in Wirtshand (2.1)
ist darum vor allem ein Umbau des Rahmens, kein neuer Codegen. Die
Kalibrierung beider Boards muss trotzdem neu laufen, weil sich der feste
Weg durch den Rahmen ändert — einmal, nachdem alle Schritte stehen, die
die Schnittstelle ändern (3 bis 11), nicht nach jedem.

**1.3 Weil die Schleife selbst wartet, ist jede Umgebung eine eigene
Bindung.** Unter `baremetal` wartet sie auf den Timer, unter `rtos` auf
eine Benachrichtigung; ein dritter Wartemechanismus wäre eine dritte
Schleife. Die Arbeit zwischen zwei Wartepunkten ist aber überall
dieselbe (12.1: abtasten, prüfen, rechnen, festschreiben, aufzeichnen).
Wird das Warten aus dem Kern herausgenommen — der Kern rechnet, was
fällig ist, und nennt die nächste Frist —, dann ist jede Umgebung nur
noch die Frage, wer ihn zur Frist ruft, und ein Port schrumpft auf eine
Handvoll Zeilen (2.3). 12.7 sieht den Host, der ein eingebettetes
Programm startet und die `sys`-Kanäle stellt, schon vor; der Kern ohne
Warten ist die Mechanik dazu. Er kommt vor allen Ports (Schritt 7).

**1.4 Die schwachen Treibersymbole sind der einzige stille Weg der
Bindung.** Alles andere an der Bindung meldet sich beim Übersetzen oder
beim Linken; ein falsch geschriebener Treibername dagegen fällt still auf
den Vorgabewert zurück. Die Referenz schließt das schon heute aus: 8.10
nennt einen gebundenen Ausgang ohne Treiber einen Bindefehler, „lieber
laut als unbemerkt“ — die schwachen Symbole sind also eine Abweichung
der Implementierung (FB-362), nicht eine offene Frage. Sie muss weg sein,
bevor ein fremdes Projekt sich darauf verlässt (Schritt 5).

**1.5 Die IEEE-Umgebung gilt nur, solange niemand sie ändert.** Heute
stellt das Board sie einmal beim Start her. In einer Einbettung läuft
der Schritt in einem Faden oder einer ISR des Wirts, dessen Code für
seine eigene Signalverarbeitung Flush-to-Zero setzen darf, und unter
einem RTOS teilt er die FPU mit anderen Aufgaben. Ein Schritt, der eine
fremde Einstellung erbt oder dessen FPU-Register ein Kontextwechsel
nicht sichert, rechnet falsch — Satz 9.4.4 wäre verletzt, ohne dass ein
Test auf dem Wirt es sähe (Schritt 6, Portprüfung in Schritt 15).

**1.6 Zwei Rahmen heißen jede Runtime-Funktion zweimal.** Der Wirtsrahmen
(`harness.rs`) und der MCU-Rahmen teilen Teile, aber nicht das Ganze;
zuletzt brauchten die Stromzähler (M10 Schritt 34) und der Schlaf mit
Eingaben (M10 Schritt 25) je einen eigenen Einbau. Das Wirtsdifferential
prüft damit einen Rahmen, den niemand ausliefert. Zusammenlegen lässt es
sich erst, wenn der Produktrahmen steht und der Kern auf dem Wirt ohne
eigenes Rust-Binary je Programm läuft: Das Differential übersetzt rund
hundert Programme, und ein `cargo build` je Programm wäre zu langsam,
eine Schleife in C eine dritte Fassung derselben Runtime. Schritt 9 folgt
darum auf den Kern (7) und das C-SDK auf dem Wirt (18a).

**1.7 ESP-IDF hält bei Flash-Zugriffen den Planer an.** Auf dem C6 stoppt
jeder Schreib- oder Löschzugriff den Instruktions-Cache; 12.3 legt den
Tick-Pfad deshalb in den RAM. Das genügt unter ESP-IDF nicht: Auf dem
einkernigen C6 hält `spi_flash_op_lock()` während des Zugriffs den
Planer an (`vTaskSuspendAll`), und `esp_intr_noniram_disable()` sperrt
jeden Interrupt, der nicht als IRAM-sicher angemeldet ist (geprüft im
Quelltext, `components/spi_flash/cache_utils.c`, v6.1-beta1). Eine
Takt-Aufgabe liefe während einer Sektorlöschung (zweistellige
Millisekunden) nicht. Das entscheidet die Form des ESP-IDF-Ports (2.5).
Der C6 kann Flash-Vorgänge auch automatisch aussetzen
(`SOC_SPI_MEM_SUPPORT_AUTO_SUSPEND`); ESP-IDF schaltet das nur auf
Wunsch ein (`CONFIG_SPI_FLASH_AUTO_SUSPEND`), weil es vom Flash-Baustein
abhängt — ob der auf Board 2 es kann, misst Schritt 21.

**1.8 Das Profil steht im Programm, gehört aber zur Einbindung.**
`system: target = rtos` beschreibt nicht das Programm, sondern wie es
eingebunden ist; dasselbe Programm kann in einem Produkt allein auf
einem Kern laufen und in einem anderen neben einem Funkstack. Und der
Name passt nicht mehr, sobald „neben fremdem Code“ auch „ohne RTOS“
heißt. Beides klärt die Referenz, bevor die Ports gebaut werden (2.6,
Schritt 1).

**1.9 M9 baut auf dieser Schnittstelle.** Der Knotenbuild von M9 ist
`takt build` je Knoten, und im Differential laufen mehrere Knoten neben
dem Interpreter. Mit Präfix und Arena aus M11 lassen sich die Knoten
eines Verbunds in einen Testprozess oder auf einen Chip binden; ohne
sie entstünde der Verbund auf der heutigen Schnittstelle und müsste nach
M11 umgebaut werden.

**1.10 Die Kalibrierung ist der teuerste Board-Schritt.** Eine Messung
des C6 dauert rund 40 Minuten, die des F401 ähnlich. Sie läuft in M11
einmal je Board, in Schritt 12, über den neuen Bausteinweg — so ist die
Kalibrierung zugleich der erste Nutzer der Schnittstelle.

## 2. Abwägungen

### 2.1 Wem gehört der Speicher? (11.2, 12.3)

Ein eingebettetes Programm braucht fünf Arten Speicher: den
veränderlichen Zustand, Stacks, Code mit Konstanten, das Journal im NVM
und die Puffer der Schleife. Die Frage ist vor allem die erste: Wer legt
den Zustand an, wo liegt er, und woher weiß der Wirt, wie groß er ist?

| Option | Mehrere Programme | Mehrere Instanzen | Platzierung durch den Wirt | Größe beim Übersetzen | Kosten im Tick | Urteil |
|---|---|---|---|---|---|---|
| A. Statisch im Rahmen, globale Namen (heute) | nein | nein | nur `.takt_state` | nur über `takt size` | Basis | trägt ein Programm, das den Chip besitzt |
| B. Statisch je Programm, mit Präfix und eigenem Abschnitt | ja | nein; zweimal übersetzen | über den Abschnitt | Konstante | Basis | trägt fremde Firmware, nicht Tests in Fäden, nicht den Verbund in einem Prozess |
| C. **Arena vom Wirt**, ein Zeiger je Eintritt | ja | ja | frei: `static`, Abschnitt, TCM, RTOS-Partition | Konstante | ein Basisregister statt vier Zeigern | **gewählt** |
| D. Heap des Wirts zur Laufzeit | ja | ja | nein | nein | Allokator im Lauf | ausgeschlossen: 12.3, kein Heap |

**Entscheidung: C, die Arena vom Wirt.** Der ganze veränderliche Zustand
eines Programms liegt in einem zusammenhängenden Block fester Größe:
Abbild, Latch, Parameter, Ψ-Doppelpuffer, Zustands-Structs mit Overlay
und Scratch (11.2), Monitore, Ringe, Warteschlangen für `at`, Job-Slots,
Randpool, Aufzeichnungspuffer, Fault-Text und eine Eintrittssperre. Der
Compiler rechnet das Layout einmal — in `takt-llvm`, für Codegen und
Rahmen gemeinsam — und gibt `ARENA_BYTES` und `ARENA_ALIGN` als
Konstanten aus; der Rahmen bestätigt jedes Feld mit
`_Static_assert(offsetof(…))`. Jeder Eintritt bekommt den Zeiger auf die
Arena; die Maschinenfunktionen rechnen mit festen Abständen von ihm aus
(ein Argument statt vier), und die Runtime-Funktionen, die der erzeugte
Code ruft (`now`, `fault`, `stream_*`, `schedule`), bekommen ihn als
erstes Argument.

Gründe:

- **Es ist die allgemeine Form, und B ist ein Sonderfall davon.** Ein
  Wirt, der genau eine statische Instanz will, schreibt eine Zeile
  (`ARENA_DEFINE`, `Arena::take()`), und die Arena liegt wie bei B in
  ihrem Abschnitt. Umgekehrt lässt sich aus B keine zweite Instanz
  machen, ohne neu zu übersetzen. Mehrere Instanzen braucht nicht die
  Firmware, aber jeder, der Firmware testet: `cargo test` fährt Tests in
  parallelen Fäden eines Prozesses, und mit statischem Zustand teilten
  sie ein Programm. Ebenso der Verbund aus M9 im Testprozess und jede
  Simulation mehrerer Geräte.
- **Der Wirt entscheidet die Platzierung, die nur er kennt.** CCM- oder
  DTCM-RAM auf einem Cortex-M7, eine Zephyr-Speicherpartition
  (`K_APP_DMEM`), eine Region für FreeRTOS-MPU, ein Abschnitt, den das
  Linker-Skript als MPU-Region ausrichtet, ein nicht genullter Abschnitt
  (`.noinit`): Das Programm sieht davon nur den Zeiger. `init` beschreibt
  die ganze Arena und verlässt sich nicht auf einen genullten `.bss`.
- **Rust kann den Besitz beweisen.** Die Hülle hält die Arena als
  `&'a mut`: Zwei Programme auf derselben Arena, ein Zugriff des Wirts
  hinein oder ein Verschieben während des Laufs übersetzen nicht. In C
  prüft die Eintrittssperre: Ein Schritt, der beginnt, während der vorige
  noch rechnet, ist eine Überschreitung und endet als `Runtime(Overrun)`
  (12.8), ein gleichzeitiger Eintritt aus einem zweiten Faden ebenso.
- **So machen es die Werkzeuge, deren Code zertifiziert wird.** SCADE
  (KCG) erzeugt je Knoten einen Kontext-Struct, den der Aufrufer anlegt
  und übergibt; Simulink Embedded Coder tut dasselbe für
  wiederverwendbaren Code. Statische Globale gibt es dort als zweite
  Form für den Ein-Instanz-Fall. Takt braucht die zweite Form nicht, weil
  das Makro sie aus der ersten macht — eine Schnittstelle, ein Pfad zum
  Zertifizieren.
- **Es kostet im Tick nichts Messbares, voraussichtlich weniger.** Der
  erzeugte Code adressiert heute über vier Zeiger, künftig über einen;
  der Rahmen adressiert über ein Basisregister statt über absolute
  Adressen, was auf RISC-V je Zugriff das `lui` sparen kann.
  Schritt 3 misst es mit `takt bench` auf beiden Boards, bevor es
  weitergeht.

Die Arena enthält Zeiger in sich selbst (der Ψ-Tausch, 11.2) und wird
nach `init` nicht bewegt; in Rust trägt das die Ausleihe, in C die
Schnittstelle. Ein Schnappschuss für `persist` geht wie heute über das
Journal, nicht über eine Kopie der Arena.

**Was nicht in die Arena gehört, und wer es stellt:**

| Teil | Größe | Wer stellt es | Wo | Schutz |
|---|---|---|---|---|
| Arena | exakt, `ARENA_BYTES`, `ARENA_ALIGN` | Wirt, einmal für die Lebensdauer | RAM nach Wahl des Wirts | 2.11 |
| Schritt-Stack | Programm exakt aus LLVM-Stack-Usage, dazu die Reserven des Ports aus `.hw` und die Marge (12.3): `TICK_STACK_BYTES` | Wirt: Hauptstack, ISR-Stack oder Stack der Takt-Aufgabe | RAM | Wächter am unteren Ende (MPU, Watchpoint oder Prüfung des RTOS) |
| Job-Stack | größter `stack`-Vertrag der Jobs plus Reserve aus `.hw`: `JOB_STACK_BYTES` | Wirt: Stack der Job-Aufgabe oder des Job-Interrupts; unter `baremetal` die Runtime im eigenen Kontext | RAM, außerhalb der Arena | Wächter, wie seit M10 Schritt 7 |
| Kern (Runtime-Struct, Telemetrie) | `size_of` in Rust, Konstante im C-SDK | Wirt | RAM | — |
| Code und Konstanten | Linker | Linker | Flash; unter `xip_flash` der Tick-Pfad im RAM (2.12) | — |
| Journal | Sektoren aus `.hw` | Wirt, in seiner Flash-Aufteilung | Flash | schreibt nur die Runtime; fremde Schreiber 2.5 |

Der Job-Stack liegt außerhalb der Arena, weil Jobs außerhalb des
Schritts rechnen, wenn die Arena nach 12.3 schreibgeschützt ist.

**Budget.** In der Einbettung ist `ram`, `flash` und `iram` in der
`.hw`-Datei der Anteil, den der Wirt Takt gibt, nicht der Chip;
Prüfung 39 hält die Summe aus Arena, Stacks und Kern dagegen. Das
Manifest (2.8) nennt die genauen Zahlen, damit der Wirt sie in seinem
eigenen Speicherplan führen kann, und `takt check-image` vergleicht sie
mit dem gebundenen Abbild. Ein RTOS-Heap ist nie beteiligt: Jeder Port
legt Fäden, Stacks und Benachrichtigungen statisch an.

### 2.2 Mehrere Programme und Instanzen in einem Abbild

**Präfix.** Jedes externe Symbol einer Programmbibliothek beginnt mit
dem Präfix des Programms: `valve_init`, `valve_service`,
`valve_<maschine>_step`, `valve_in_<adr>`. Vorgabe ist der Dateiname;
er muss ein C-Bezeichner sein und darf nicht `takt` heißen. Erwogen war,
Codegen und Rahmen zu einem Objekt zu binden und alles außer den
Einstiegen lokal zu machen (`ld -r` und `objcopy --keep-global-symbols`).
Das geht auf ELF, nicht auf COFF, und der Wirtstest unter Windows läuft
über COFF. Das Präfix geht überall gleich.

**Geteilte Bibliotheken.** `libtaktm` (`takt_m_*`), die kuratierten
Natives (`takt_native_*`), der Randkern (`takt_edge_*`) und der Kern
sind in einem Abbild einmal vorhanden, auch bei mehreren Programmen,
und unter `xip_flash` liegen ihre Tabellen einmal im RAM. Das verlangt,
dass sie keinen veränderlichen Zustand haben. Ein Test prüft es über die
Archive (`nm`: kein Symbol in `.data` oder `.bss`), und das Prüfgerät des
Rands (`takt-driver-probe`) bekommt seinen Tick über den Wirtszeiger
statt über die globale `takt_mcu_current_tick()`.

**Mehrere Programme auf einem Kern.** Jedes Programm hat seinen Tick,
seine Arena und seinen Kontext; der schnellere Tick bekommt die höhere
Priorität (ratenmonoton). Ohne RTOS heißt das: je Programm eine
Timer-ISR, verschachtelt nach Priorität wie unter RTIC; unter einem RTOS
je Programm ein Faden. Die Semantik bleibt je Programm unberührt: Die
Arenen sind getrennt, und Programme tauschen nur über Kanäle aus, die der
Wirt mit Treibern verbindet — mit den Regeln des Rands (12.6) auf beiden
Seiten, wie zwischen zwei Steuergeräten. Gemeinsamen Speicher zwischen
Programmen gibt es nicht. Die Zeit dagegen teilen sie: Das niedrigere
Programm sieht das höhere als Störung. `takt check-image` rechnet über
die Manifeste aller Programme eines Kerns die Auslastung und die
Antwortzeiten mit festen Prioritäten, aus den kalibrierten Budgets und
der Störung, die die `.hw`-Datei für fremden Code nennt. Das Ergebnis hat
den Ursprung „Vertrag“ (11.5), weil die fremde Last angegeben und nicht
bewiesen ist; die gemessene `drift` im Lauf bestätigt es oder widerlegt
es.

**Mehrere Instanzen** eines Programms teilen Code und Bibliothek; jede
hat ihre Arena, ihr Treiberobjekt (über den Wirtszeiger), ihr Journal
und ihren Kern.

### 2.3 Der Portvertrag: Takt wartet nie selbst (12.1, 12.7)

| Option | Was ein neues RTOS braucht | Ohne RTOS neben fremdem Code | Urteil |
|---|---|---|---|
| a. Eine Bindung je Umgebung, jede mit eigener Schleife (heute: `baremetal`, RTIC) | eine neue Schleife in Rust | eine weitere Bindung | verworfen: wächst mit jeder Umgebung, jede Schleife ist TCB |
| b. Eine Schleife mit Rückrufen für Warten, Benachrichtigen, Aufgaben anlegen (Trait oder Funktionstabelle) | die Rückrufe | Rückrufe, die es dort nicht gibt (Warten in einer ISR) | trägt RTOS, nicht ISR und Hauptschleife |
| c. **Kern ohne Warten**: rechnet, was fällig ist, und nennt die nächste Frist; der Wirt ruft ihn | eine Uhr und einen Kontext, der zur Frist ruft | dieselbe Form, aus der Timer-ISR oder der Schleife | **gewählt** |

**Entscheidung: c.** Der Kern hat zwei Einstiege, beide blockieren nie:

- `service(now) → next` rechnet alle Tickgrenzen bis `now` nach 12.1 —
  abtasten, prüfen, Ströme liefern, Schritt, Abort-Phase, Commit,
  Aufzeichnung, Journal, Ende des Laufs — und gibt zurück, wann er
  wieder gerufen werden will (`deadline`), ob Jobs warten (`jobs`) und
  ob der Lauf geendet hat (`ended`). Ist Schlaf nach 9.9 erlaubt, ist
  `deadline` die Frist aus 9.9 statt der nächsten Tickgrenze; ob der Wirt
  die Zeit verschläft oder anders nutzt, ist seine Sache, und Satz 9.9.1
  sagt, dass der Trace davon nicht abhängt.
- `job_work()` rechnet wartende Jobs (4.5), unterbrechbar durch
  `service`, und kehrt zurück, wenn keiner mehr wartet.

Ruft der Wirt `service` zu spät, misst der Kern die Verspätung als
`drift` (7.3); jenseits der Toleranz ist es `Runtime(Overrun)`, wie
heute. Ruft er zu früh, ist nichts fällig. Die bestehenden Schleifen
werden zu Ports über diesem Kern: `baremetal` wartet mit
`Clock::wait_until` auf `deadline` und ruft `service`.

**Der Vertrag.** Pflicht für jeden Port ist dreierlei:

1. **Uhr:** eine monotone Zeit in Nanosekunden (oder Zähler und
   Frequenz).
2. **Schrittkontext:** ruft `service` zu oder nach jeder `deadline`, nie
   zwei Aufrufe gleichzeitig; sichert beim Kontextwechsel die
   FPU-Register (2.10); hat `TICK_STACK_BYTES`; liegt über allem, was
   Takt-Kanäle bedient, in der Priorität.
3. **Job-Kontext** — nur, wenn das Programm Jobs hat: ein Kontext
   niedrigerer Priorität, der `job_work` ruft, wenn `jobs` gesetzt ist,
   mit `JOB_STACK_BYTES`.

Alles andere sind **Dienste nach Bedarf**, und das erzeugte Interface
verlangt nur die, die das Programm nutzt: ein Gerät für das Journal
(nur mit `persist`), die Plattformbefehle für `sys/next_run` und die
Quelle für `sys/previous_run` (nur, wenn das Programm sie liest oder
schreibt; 12.7 legt sie schon heute in die Hand des Hosts), die Meldung
an den Watchdog des Wirts, eine Senke für Telemetrie und Aufzeichnung,
und die Art des Speicherschutzes (2.11). Ein Programm ohne Jobs und ohne
`persist` braucht vom Wirt also nur Uhr, Schrittkontext und Treiber.

**Wem was gehört.** Takt besitzt seinen Lauf (12.7), nicht den Chip.
Unter `baremetal` gehören Schlaf, Watchdog und Neustart der Runtime wie
heute (12.3). In jeder anderen Form gehören sie dem Wirt: Der Kern bietet
den Schlaf über `deadline` an, meldet dem Watchdog des Wirts, dass er
lebt, und übergibt `sys/next_run` als Plattformbefehl; den Chip schlafen
legen, den Watchdog füttern und neu starten tut der Wirt, weil nur er
weiß, was außer Takt noch läuft.

### 2.4 Ohne RTOS neben fremdem Code

Drei Formen, alle über denselben Kern:

| Form | Schritt | Jobs | Zeitgarantie | Wann |
|---|---|---|---|---|
| **Interruptform** | Timer-ISR ruft `service`, stellt den Timer auf `deadline` | Interrupt niedrigster Priorität (Cortex-M: ein freier Interrupt oder PendSV; C6: Software-Interrupt `FROM_CPU`) | gemessen; Störung nur durch höher priorisierte ISRs und kritische Abschnitte des Wirts | der Regelfall: Die Hauptschleife des Wirts bleibt unberührt |
| **Pollform** | die Hauptschleife ruft `service`, wenn `deadline` erreicht ist | ohne Jobs, oder Jobs in einem Interrupt wie oben | gemessen; Störung durch die längste Runde der Hauptschleife | einfache Projekte, langsame Ticks, Programme ohne Jobs |
| **Eigener Kern** | wie heute unter `baremetal`: der Port wartet auf `deadline` | eigener Kontext (M10 Schritt 7) | statisch, Budget mal Tabelle | Takt allein auf dem Kern |

Der Bau kennt die Form und prüft, was sich prüfen lässt: Pollform mit
Jobs ohne Job-Interrupt ist ein Baufehler, ebenso ein Programm, dessen
Tick kürzer ist als die angegebene längste Runde der Hauptschleife.
Mehrere Programme ohne RTOS sind mehrere Timer-ISRs nach Priorität
(2.2). Die Interruptform ist zugleich das, was RTIC und Embassy tun —
deren Ports sind die Interruptform mit dem Planer des Frameworks.

### 2.5 Unter einem RTOS: Ports auf drei Stufen

Ein RTOS-Port besteht aus vier Grundfunktionen: Benachrichtigen aus der
Timer-ISR, Warten in der Takt-Aufgabe, eine Aufgabe mit statischem Stack
anlegen, und — wo vorhanden — die Arena in eine Partition legen. Die
Takt-Aufgabe ist eine Schleife aus Warten, `service` und Timer stellen;
die Job-Aufgabe wartet auf `jobs` und ruft `job_work`. Für ein RTOS, das
Takt nicht kennt, sind das rund vierzig Zeilen C.

**Stufe 1, eigene Ports** — dort, wo die Umgebung mehr bietet als die
vier Grundfunktionen, und jeder auf Hardware geprüft:

| Port | Was er über die Grundfunktionen hinaus tut | Geprüft auf |
|---|---|---|
| Rust, Interruptform | Timer und Job-Interrupt für die Board-Crates; der Kern in einem `static` mit `critical-section` | F401, C6 |
| RTIC 2 | der bestehende Aufsatz, umgestellt auf den Kern | F401 |
| Embassy | eine Aufgabe auf einem `InterruptExecutor` hoher Priorität; der Timer aus `embassy-time` | F401, C6 |
| Zephyr | Modul mit `module.yml`, `Kconfig` (`CONFIG_TAKT`, Prioritäten, Zeitgeber) und `takt_add_program`; Faden mit `K_FP_REGS`; Hardware-Zeitgeber über die `counter`-API, wenn der Devicetree einen nennt, sonst `k_timer`; Arena in einer Partition (`K_APP_DMEM`); Treiberadapter aus dem Devicetree (2.7) | F401 (`blackpill_f401cc`), C6 (`esp32c6_devkitc`) |
| FreeRTOS | statische Aufgaben (`xTaskCreateStatic`), Benachrichtigung aus der ISR (`vTaskNotifyGiveFromISR`), die Timer-ISR nicht über `configMAX_SYSCALL_INTERRUPT_PRIORITY`; FreeRTOS-MPU, wenn eingeschaltet | F401 |
| ESP-IDF | der Schritt in einer IRAM-ISR des `gptimer`, Jobs in einer Aufgabe, das Journal in einer eigenen Partition; das automatische Aussetzen als zweite Form, wenn der Flash-Baustein es kann (1.7) | C6 mit aktivem Funk |
| Linux (`linux_rt`) | Tick-Faden mit `clock_nanosleep` auf absolute Fristen, `mlockall`, vorab berührte Seiten — jetzt mit der Arena —, die Zusage im Header (12.2) | x86-64 |
| Wirt, logische Zeit | der Test ruft `service` selbst, so schnell er will; Determinismus und Trace bleiben, eine Zeitgarantie gibt es nicht, und der Header sagt das | Windows, Linux |

**Stufe 2, generische Ports** — einer für viele RTOS, auf einer Plattform
geprüft:

- **CMSIS-RTOS2** (`osThreadNew` mit statischem Speicher,
  `osThreadFlagsSet` aus der ISR, `osThreadFlagsWait`): Die Schnittstelle
  bieten unter anderem Keil RTX5, FreeRTOS (CMSIS-FreeRTOS) und Zephyr
  an. Geprüft unter Zephyrs CMSIS-RTOS2-Schicht auf dem F401.
- **POSIX** (`pthread`, `clock_nanosleep` mit `TIMER_ABSTIME`): unter
  anderem NuttX, RTEMS, QNX und Linux ohne `linux_rt`-Zusage. Geprüft
  unter Linux.

**Stufe 3, jedes andere RTOS:** der Vertrag aus 2.3, ein Port nach dem
Muster der Vorlage `c-port`, und die Portprüfung (2.9), die belegt, dass
er trägt. Ein Port, der sie besteht, ist so gut wie ein mitgelieferter;
ihr Ergebnis steht im Konformitätsbericht.

**Fremde Flash-Schreiber unter `xip_flash`.** Ohne RTOS genügt der
Tick-Pfad im RAM (12.3), wenn die Interruptform den Schritt rechnet und
der Wirt beim Flash-Schreiben die Interrupts nicht sperrt. Unter ESP-IDF
genügt es nicht (1.7). Drei Wege: (a) Der Schritt läuft in einer
IRAM-ISR, die ESP-IDF während Flash-Zugriffen weiterlaufen lässt; (b)
das automatische Aussetzen, das auch die Aufgabe laufen ließe; (c) der
Wirt schreibt den Flash nur in Fenstern, die Takt freigibt.
**Entscheidung: (a)** als Form des ESP-IDF-Ports, weil sie nur von einer
Zusage abhängt, die ESP-IDF dokumentiert und im Quelltext einhält; (b)
als zweite Form, wenn Schritt 21 sie auf Board 2 belegt; (c) legte dem
Wirt eine Pflicht auf, die er vergessen kann. Unter (a) muss auch der
Treibercode im IRAM liegen; `takt check-image` prüft das (2.12).

**Funk.** 12.8 schließt Bare-Metal-Funk aus, weil er nicht
deterministisch ist. Gemeint ist ein Funkstack in der Runtime von Takt.
Neben Takt ist ein Funkstack fremder Code wie jeder andere — unter einem
RTOS oder als `no_std` mit eigenem Heap neben Embassy —, er gehört zur
TCB, die Garantie ist gemessen, und Funkdaten kommen als Streams über
den Rand. Der Satz wird präzisiert (Nachzug 7.8), und die Messung „bei
aktivem Funk“ aus `plan/m10.md` 2.5 entsteht in Schritt 21.

**Störung durch fremden Code.** Fremde ISRs über dem Schritt verzögern
ihn, fremde kritische Abschnitte sperren ihn. Beides misst `takt bench`
unter der Last des Wirts (13.8) und schreibt es als `tick_jitter_ns` in
die Konfiguration; die Prüfungen der Planbarkeit rechnen damit wie
heute.

### 2.6 Das Profil: aus der Einbindung, mit passendem Namen (12.8)

12.8 kennt drei Profile, und was sie unterscheidet, ist die
Zeitgarantie: statisch, wenn Takt den Kern allein hat (`baremetal`),
gemessen unter Linux (`linux_rt`) und gemessen, wenn fremder Code den
Kern teilt (`rtos`). Ein viertes Profil „eingebettet“ hätte die dritte
Zeile ein zweites Mal geschrieben; es kommt nicht. Zwei Dinge ändern
sich:

- **Das Profil kommt aus der Einbindung.** Die Form, die der Bau kennt,
  bestimmt es: eigener Kern → `baremetal`, Interrupt- und Pollform und
  jedes RTOS → das dritte Profil, Linux → `linux_rt`. Ein Programm darf
  `system: target` weglassen; nennt es ein Profil, das der Einbindung
  widerspricht, ist das ein Baufehler mit Vorschlag. So läuft dasselbe
  Programm ohne Änderung allein auf einem Kern und neben einem
  Funkstack.
- **Das dritte Profil heißt `shared`** („Takt teilt den Kern mit fremdem
  Code“), seit 2026-10-02 und in Edition 1. `rtos` beschreibt die
  Interruptform neben einer eigenen Hauptschleife falsch, und ein Name,
  der in die Irre führt, kostet jeden neuen Leser Zeit. Erwogen war, den
  Namen zu lassen und nur die Prosa zu ändern: Weil das Profil künftig
  meist aus der Einbindung kommt, stünde das Wort seltener im Programm,
  aber im Lauf-Header und im Bericht stünde es immer. Erwogen war auch
  eine neue Edition mit `rtos` als Alias. Dagegen sprach: `takt migrate`
  kommt erst mit M7, kein Programm im Korpus nannte `rtos`, im Code stand
  der Name an sechs Stellen, und die Referenz hat für eine solche
  Änderung in Edition 1 einen Vorgang (`f.data`, Anhang A) — je später,
  desto teurer. Ein Programm mit `target = rtos` bekommt einen Fehler,
  der den neuen Namen nennt.

Die Form steht im Lauf-Header neben dem Profil (`shared/zephyr`,
`shared/isr`, `shared/poll`, `shared/esp-idf`, …), damit eine Aufzeichnung
sagt, unter welchen Umständen sie entstand.

### 2.7 Treiberschnittstelle: typisiert, stark gebunden, mit Adaptern (12.6)

| Option | Fehlender oder falsch benannter Treiber | Mehrere Instanzen | Aufruf im Tick | Urteil |
|---|---|---|---|---|
| a. Schwache Symbole mit Vorgabe (heute) | still der Vorgabewert | nein | direkt | verworfen: der stille Weg aus 1.4 |
| b. Funktionstabelle, bei `init` übergeben | in Rust ein Übersetzungsfehler, in C ein Nullzeiger, den `init` meldet | ja, je Tabelle | indirekt, nicht inlinebar | trägt, kostet je Kanal und Tick einen indirekten Sprung |
| c. **Starke Symbole mit Präfix und Wirtszeiger** | Rust: Übersetzungsfehler, C: Link-Fehler | ja, über den Wirtszeiger | direkt, mit LTO inlinebar | **gewählt** |

**Entscheidung: c.** Der Rahmen ruft `valve_in_pressure(user, &value,
&quality, &t)`; `user` ist der Zeiger, den der Wirt bei `init` übergab.
Für Rust erzeugt das Bauskript den Kleber zu dem Typ, den es nennt
(`.drivers("crate::io::Board")`): einen `extern "C"`-Einstieg je Kanal,
der die Methode des Traits `valve::Drivers` ruft. Fehlt eine Methode,
übersetzt die Firmware nicht, und die Meldung nennt Kanal und Methode;
fehlt in C eine Funktion, linkt sie nicht, und der Name
(`valve_in_pressure`) sagt, welcher Kanal fehlt. Der Kleber ist
monomorph, weil `extern "C"`-Funktionen nicht generisch sein können;
eine zweite Instanz mit einem anderen Treibertyp ist ein zweites Präfix.

Schwache Vorgaben verschwinden überall, auch aus den Testrahmen: Ein
Test, der einen Kanal ohne Treiber lässt, erzeugt dafür ausdrücklich
einen Stummel. Der ist im Bau sichtbar; ein Vorgabewert war es nicht.
Das Prüfgerät des Rands und die Treiber-Crates aus M10 Schritt 11c
erfüllen danach denselben Trait, und `takt driver-test --crate` prüft
sie über ihn.

Die Werte im Trait sind die des Rands: `Sample<T> { value, quality, t }`
für Skalare, ein Stück mit Länge, Zeit und `seq` für Streams, ein `bool`
für die Annahme eines Ausgangs, dazu `alive` und `free` (12.6). Das
C-Interface nutzt nur Typen fester Breite, keine C-Enums und keine
Strukturen mit Polsterung, damit eine Bibliothek aus `clang` mit einer
Firmware aus GCC zusammenpasst, auch bei abweichenden Voreinstellungen
wie `-fshort-enums`.

**Adapter für die häufigen Kanäle.** Die meisten Kanäle eines Projekts
sind ein Pin, ein ADC-Kanal oder eine serielle Schnittstelle. Für sie
schreibt der Entwickler keinen Treiber:

- **Rust:** Adapter auf `embedded-hal` 1.0 (`InputPin`, `OutputPin`) und
  `embedded-io` (Byte-Ströme) — ein Treiberobjekt besteht dann aus den
  Peripherie-Objekten seines HAL.
- **Zephyr:** Die `.hw`-Datei nennt für einen Kanal einen Devicetree-Knoten
  (`zephyr = "valve"`), und der Port erzeugt den Treiber über
  `gpio_dt_spec`, `adc_dt_spec` oder ein UART-Gerät.
- **Stream-Treiber, die aus einer ISR liefern:** ein Ring für einen
  Schreiber und einen Leser in `takt-embed` und im C-SDK, sodass der
  Treiber in seiner ISR schreibt und `poll` im Schritt liest, ohne
  eigene Sperre.

Die Adapter erfüllen die Regeln des Rands wie jeder Treiber und gehen
durch `takt driver-test`.

### 2.8 Lieferform und Bausysteme (11.1)

**Ein Aufruf liefert alles.** `takt build PROGRAMM --emit embed --target
TRIPEL --hardware DATEI.hw --form FORM [--prefix P]` schreibt:

| Datei | Inhalt |
|---|---|
| `libP.a` (`P.lib` für MSVC) | erzeugter Code und Rahmen, übersetzt mit dem `clang`, den Takt ohnehin braucht |
| `P.h` | Konstanten, Arena-Typ und `P_ARENA_DEFINE`, Einstiege, Treiberprototypen mit Einheit, Bereich und Rate als Kommentar, Kanalnummern |
| `P.rs` | dieselben Konstanten, `Arena`, Trait `Drivers` mit Dokumentation je Kanal, die sichere Hülle `Program`, den Kleber zum Treibertyp |
| `P.manifest` | Präfix, ABI-Version, Logik-Hash, Ziel, Profil und Form, Arena, Stacks, Budget, NVM-Bedarf, `mmio`-Regionen, die Einstiege des Tick-Pfads, die verlangten Dienste; versioniert wie der Konformitätsbericht |
| `P_ram.x`, auf Wunsch `P.lf` | unter `xip_flash` das Fragment, das den Tick-Pfad in den RAM legt: für GNU ld und lld, für ESP-IDF als `ldgen`-Fragment |

Das Tripel kommt vom Wirt (Cargo `TARGET`, CMake-Toolchain); `takt-llvm`
bildet es auf ein Takt-Ziel ab, einschließlich der Float-ABI. Passt sie
nicht zur Zielklasse der `.hw`-Datei — etwa `thumbv7em-none-eabi` ohne
FPU zu einer Klasse mit f32-FPU —, meldet `takt build` den Widerspruch,
statt still auf Soft-Float umzuschalten. M11 nimmt die Tripel der
Zielklassen auf, die Rust und LLVM für Mikrocontroller kennen
(`thumbv6m`, `thumbv7m`, `thumbv7em`, `thumbv8m.main`, `riscv32imc`,
`riscv32imac`, `riscv32imafc`); kalibriert sind davon nur die beiden
Boards, für die anderen gilt die Kostentabelle der Klasse, bis jemand
misst.

**Die geteilten Teile.** Ein Rust-Wirt bekommt `libtaktm`, die Natives,
den Randkern, den Kern und die Ports als Crates. Ein C-Wirt bekommt sie
als SDK-Archiv je Ziel (`libtakt_sdk.a`, Crate `takt-embed-c`, eine
C-Schnittstelle zu Kern und Ports), gebaut im Freigabeprozess von Takt.
Den Kern in C nachzubauen, hätte eine zweite Runtime ergeben.

**Dünne Adapter je Bausystem.** `takt-embed` ist der Bauhelfer für
`build.rs` und ruft das Werkzeug, nicht die Bibliothek — das Prinzip aus
FB-138, nach dem ein Bauskript nicht anders übersetzen darf als `takt
build`; er meldet `rerun-if-changed` für Programm und `.hw`-Datei und
gibt Diagnosen mit Datei und Zeile weiter. `tools/cmake/Takt.cmake`
stellt `takt_add_program(valve SOURCE valve.takt HARDWARE board.hw)`
bereit und ist zugleich ein CMake-Paket (`find_package(Takt)`); das
Zephyr-Modul und die ESP-IDF-Komponente (`idf_component.yml`) umhüllen
es. Kein Adapter enthält eigene Logik.

**Eine Schnittstelle für alle.** Der Rahmengenerator zieht in ein Crate
`takt-frame` (im Workspace, ohne `unsafe`); `takt-conformance` nutzt
ihn wie jeder andere. Die Bring-ups beider Boards und `takt-bringup-host`
binden über `takt-embed`, `takt-mcu-program` geht im erzeugten Modul
auf, und das Wirtsdifferential fährt den Produktrahmen mit einem
Stimulus als Testtreiber und dem Dump als Senke statt eines eigenen
Rahmens (1.6). Was die Board-Suiten prüfen, ist dann genau das, was ein
fremdes Projekt bindet.

**Versionen.** Die Bibliothek definiert ein Symbol `P_abi_<n>`, das die
erzeugte Hülle referenziert: Passen Bibliothek und Hülle nicht
zusammen, bricht der Link, nicht der Lauf. Der Logik-Hash steht im
Manifest, im Lauf-Header und im Journal, das ihn schon heute prüft.

### 2.9 Entwicklererfahrung

Die Garantien von Takt helfen niemandem, der am ersten Nachmittag
scheitert. Darum hat M11 eigene Abnahmen für die Erfahrung (Abschnitt 0)
und folgt vier Grundsätzen:

**Ein Befehl zum ersten Lauf.** `takt new --embed <form> NAME` legt ein
Projekt aus einer Vorlage an — je Form aus 2.4 und je Port aus 2.5
eine. Die Vorlagen sind die Beispiele aus `examples/`, und die CI baut
und testet jede: Eine Vorlage, die nicht baut, kann nicht ausgeliefert
werden. `takt doctor --target TRIPEL` sagt vorher, ob `clang`, `llvm-ar`
und das Ziel bereitstehen und wie alt die Kalibrierung der `.hw`-Datei
ist.

**Fehler beim Bauen, nicht im Lauf.** Was der Bau erkennen kann, ist ein
Baufehler mit Ursache und Vorschlag:

| Verletzung | Meldung beim Bau |
|---|---|
| Treiber fehlt oder ist falsch benannt | Rust: fehlende Methode des Traits mit Kanal; C: Link-Fehler mit dem Kanalnamen im Symbol |
| Dienst fehlt (Programm nutzt `persist`, der Wirt gibt kein Journal) | Rust: fehlendes Argument im Konstruktor; C: Link-Fehler auf den Dienst |
| Pollform mit Jobs ohne Job-Kontext | Fehler der Form, Vorschlag Job-Interrupt |
| Profil im Programm widerspricht der Form | Fehler mit beiden Namen, Vorschlag `system: target` weglassen |
| Float-ABI des Tripels passt nicht zur Zielklasse | Fehler mit Tripel und Klasse |
| Budget überschritten (Prüfung 39) | Fehler mit Arena, Stacks und Anteil aus der `.hw`-Datei |
| Bibliothek und Hülle verschiedener ABI-Version | Link-Fehler auf `P_abi_<n>` |

Was erst das gebundene Abbild zeigt — Treiber im Flash, beschreibbare
Symbole außerhalb der Arena, zu kleine Stacks —, meldet
`takt check-image` (2.12), und die Vorlagen hängen es in ihren Bau.

**Tests auf dem PC ohne eigene Arbeit.** Jede Programmbibliothek gibt es
auch für den Wirt. `takt-embed` bringt eine Testhilfe mit, die das
Programm in logischer Zeit fährt, Treiber aus einem Stimulus speist und
den Trace mit dem Interpreter vergleicht
(`valve::testing::same_as_interpreter(stimulus)`) — die Konformität aus
13.1 als eine Zeile im Test des Entwicklers. Instanzen laufen parallel
(2.1).

**Ein neuer Port ist belegt, nicht geglaubt.** `takt port-test` erzeugt
ein Prüfprogramm als Baustein: eine Auswahl aus dem Korpus mit Jobs,
`at`, Strömen und `persist`, einen Kern, der lange mit der FPU rechnet,
während eine fremde Aufgabe dasselbe tut, eine Messung von `drift` und
Hochwassermarken. Der Port fährt es, schreibt die Ausgabe in eine Senke,
und `takt port-test --judge LOG` urteilt: Trace gleich dem Interpreter,
FPU-Kontext gesichert, Jobs unterbrechbar, Stacks unter der Schranke,
Jitter. Das Urteil steht im Konformitätsbericht (13.8). Jeder
mitgelieferte Port besteht es in der Board-Suite; ein fremder Port
bekommt dasselbe Werkzeug.

Dazu kommen Senken für die Telemetrie, die ein Entwickler ohnehin hat:
`defmt` über RTT (Rust), das Zephyr-Log, das ESP-IDF-Log, eine UART und
eine Datei unter Linux. `takt replay` liest, was sie aufzeichnen.

### 2.10 Rechnen in fremder Umgebung (4.2)

Was Takt rechnet, ist Sprache, nicht Chip: Grundrechenarten nach IEEE
754, `libtaktm` korrekt gerundet, die `_fast`-Familie als
deterministische Näherung mit dokumentierter Schranke (4.2) — die
Ergebnisse sind auf jedem Ziel bitgleich. Am Chip hängt nur die Zeit,
und die steht vor dem Lauf in der Kostentabelle (12.8, Zielklassen). Die
Einbettung muss dafür zweierlei sichern:

**Die IEEE-Umgebung an jedem Eintritt.** Jeder Eintritt in Takt-Code —
`init`, `service`, `job_work`, die Haken des Journals — sichert das
Steuerregister des Wirts, setzt die IEEE-Vorgabe (zur nächsten runden,
kein Flush-to-Zero, keine Default-NaN) und stellt beim Austritt das des
Wirts wieder her: auf Cortex-M und armv7 `FPSCR`, auf x86-64 `MXCSR`,
auf aarch64 `FPCR`, auf RV32F `fcsr`; auf dem C6 ohne FPU entfällt es.
Erwogen war, nur zu prüfen und bei Abweichung einen Fault zu werfen. Das
verwehrte dem Wirt eine Einstellung, die für seinen eigenen Code
legitim ist, und machte Takt-Faults von fremdem Code abhängig. Setzen
und Zurückgeben kostet zwei bis vier Befehle je Eintritt; Schritt 6
misst es.

**Die FPU-Register über Kontextwechsel.** Rechnet eine andere Aufgabe
mit der FPU, muss das RTOS die Register der Takt-Aufgabe sichern. Das
ist Pflicht des Ports (2.3): unter Zephyr `K_FP_REGS`, unter FreeRTOS der
Port mit FPU (`ARM_CM4F`), auf Cortex-M ohne RTOS das verzögerte Sichern
der Hardware. Die Portprüfung prüft es mit einer fremden Aufgabe, die
gleichzeitig rechnet.

**Die Kosten der Mathematik.** Unter `xip_flash` liegen `libtaktm` und
ihre Tabellen im RAM (FB-357); bei mehreren Programmen einmal. Ein
Entwickler, der auf einem Chip ohne FPU rechnet, sieht die Kosten von
`f64` in der Tabelle, bevor das Programm läuft, und wählt `f32`,
`int[U]` oder die `_fast`-Familie dort, wo die Fehlerschranke reicht.

### 2.11 Speicherschutz neben fremdem Code (12.3)

12.3 schützt den Programmzustand gegen die TCB: eine eigene Region, nur
im Schritt beschreibbar. Neben fremdem Code kommt ein zweiter Gegner
dazu, der fremde Code selbst — ein Stacküberlauf einer fremden Aufgabe,
ein wilder Zeiger im Funkstack. Wer die MPU besitzt, entscheidet, was
möglich ist:

| Wem die MPU gehört | Schutz der Arena | Kopfzeile |
|---|---|---|
| Takt: eigener Kern, Interrupt- und Pollform, RTIC, Embassy | wie 12.3: eigene Region, nur im Schritt beschreibbar; fremder Code schreibt außerhalb des Schritts nicht hinein. Unterbricht eine fremde ISR den Schritt, ist die Region für sie offen. | `Schutz: Fenster` |
| das RTOS: Zephyr mit `CONFIG_USERSPACE`, FreeRTOS-MPU, die PMP unter ESP-IDF | die Arena liegt in einer Partition, die nur die Takt-Aufgabe beschreiben darf; geschützt ist sie gegen Aufgaben im Benutzermodus, nicht gegen privilegierten Code. Das Zeitfenster entfällt, weil es je Tick Aufrufe des RTOS bräuchte. | `Schutz: Partition` |
| niemand: keine MPU, oder das RTOS lässt keine Region zu | keiner; fremder Code im selben Adressraum gehört zur TCB | `Schutz: keiner` |

Die Kopfzeile steht im Lauf-Header (11.3) und im Konformitätsbericht:
Ein schwächerer Schutz ist sichtbar, nicht angenommen. Für
sicherheitsrelevante Produkte gilt die Empfehlung aus 12.8 weiter: Takt
auf einem eigenen Chip. `plan/cert.md` bekommt die TCB-Zeilen der
Einbettung (fremder Code im Adressraum, Treiber des Wirts, RTOS, Port).
Für den Fall „Fenster“ verlangt die ARMv7-M-MPU eine Region mit
Zweierpotenz als Größe, ausgerichtet auf diese Größe; `ARENA_ALIGN`
folgt dann aus der `.hw`-Datei (`protect`), und die Arena wächst auf die
nächste Zweierpotenz.

### 2.12 Kalibrieren und prüfen, was gebunden wurde (13.8, 11.5)

**Kalibrierung eigener Boards.** Heute braucht `takt bench` ein Bring-up
je Board. Künftig ist das Messprogramm selbst ein Baustein: `takt bench
--emit embed` liefert es als Bibliothek, der Wirt stellt zwei Haken —
einen Zykluszähler und eine Byte-Senke — und ruft es auf; `takt bench
--import LOG` schreibt `.hw` und `.report`. Die eigenen Bring-ups messen
auf genau diesem Weg (Schritt 12). Neben fremdem Code misst der Wirt
einmal ohne und einmal mit seiner Last; der Jitter unter Last ist der,
mit dem die Prüfungen rechnen.

**`takt check-image ABBILD --manifest P.manifest …`** prüft das fertig
gebundene ELF, nicht die Annahmen davor:

1. ABI-Version und Logik-Hash jeder gebundenen Programmbibliothek;
2. Arena-Symbole nach Größe und Ausrichtung gegen das Manifest, und kein
   beschreibbares Symbol aus Takt-Bibliotheken außerhalb der Arenen;
3. unter `xip_flash`: Jede Funktion, die vom Tick-Pfad aus erreichbar ist,
   liegt im RAM, auch die Treiber des Wirts; Ausnahme sind Wege, die nur
   vor einer Panik laufen. `takt-llvm/src/inspect.rs` liest heute
   Abschnitte und Stackrahmen aus der Disassemblierung; der Aufrufgraph
   kommt dazu. Das ist die Prüfung, die für FB-357 von Hand lief;
4. die Stacks, wenn der Wirt ihre Symbole im Manifest nennt; unter
   Zephyr und FreeRTOS findet der Port sie selbst;
5. mit mehreren Manifesten eines Kerns: Auslastung und Antwortzeiten
   (2.2).

Jede Zeile trägt ihren Ursprung (exakt, Vertrag, gemessen, offen; 11.5).
Die Vorlagen hängen `check-image` in den Bau, ein fremdes Projekt in
seine CI.

### 2.13 Was M11 nicht tut

- **Keinen Heap und kein Nachladen.** Weder Allokation zur Laufzeit noch
  Programme als ladbare Bibliotheken oder Austausch im Lauf; ein Update
  ist Sache des Wirts, Logik-Hash und Journal prüfen die Verträglichkeit
  wie heute.
- **Keine eigenen Ports über die Liste in 2.5 hinaus.** Weitere RTOS
  tragen die generischen Ports oder ein Port nach dem Vertrag; die
  Portprüfung belegt ihn.
- **Keine Veröffentlichung in Registries.** Die Formate dafür entstehen
  (Crate, CMake-Paket, Zephyr-Modul, ESP-IDF-Komponente); ob und wann
  sie auf crates.io, in der Espressif-Registry oder in einem
  West-Manifest erscheinen, entscheidet die Freigabe von Takt.
- **Keine C++-Hülle.** Der Header ist mit `extern "C"` aus C++ nutzbar.
- **Keinen gemeinsamen Speicher zwischen Programmen.** Programme koppeln
  über Kanäle, mit dem Rand auf beiden Seiten.
- **Keine Änderung der Semantik**, und nichts aus M9; der Knotenbuild
  nutzt die Schnittstelle aus M11.

## 3. Arbeit je Werkstück

### takt-frame (neu)

Der Rahmengenerator aus `takt-conformance` (`mcu.rs` und die geteilten
Teile von `harness.rs`, `streams.rs`, `edge.rs`), zuerst ohne
Verhaltensänderung (Schritt 2). Danach: die Arena statt statischer
Puffer, `_Static_assert` je Feld, Präfix, starke Treibersymbole mit
Wirtszeiger, Eintrittssperre, IEEE-Umgebung an jedem Eintritt, Header
und Rust-Modul mit Dokumentation je Kanal.

### takt-llvm

Eine Layoutrechnung der Arena für Codegen und Rahmen; der Arena-Zeiger
als einziges Argument der Maschinenfunktionen und als erstes der
Runtime-Funktionen; die drei Fault-Globalen in die Arena; Präfix aller
externen Symbole; die Tripel der Zielklassen mit Float-ABI; Aufrufgraph
und Erreichbarkeit vom Tick-Pfad in `inspect.rs`.

### takt-sema, takt-mir

Das Profil aus der Einbindung, `system: target` optional. `shared` statt
`rtos` ist seit Schritt 1 umgesetzt.

### takt-cli

`takt build --emit embed` mit `--form` und `--prefix`; `takt new
--embed`; `takt doctor`; `takt check-image`; `takt port-test` und
`--judge`; `takt bench --emit embed` und `--import`; `takt size` nennt
die Konstanten des Manifests.

### takt-rt-core, takt-rt-baremetal, takt-rt-rtos, takt-rt-linux

Der Kern ohne Warten (`service`, `job_work`, Dienste nach Bedarf) in
`takt-rt-core`; `baremetal` als Port „eigener Kern“ darüber; RTIC
umgestellt, Embassy und die Interruptform neu; `takt-rt-linux` mit
erzeugtem Code.

### takt-embed, takt-embed-c (neu, eigene Workspaces)

`takt-embed`: der Bauhelfer für `build.rs`, die Typen der Hülle (`Arena`,
`Sample`, Stücke), die Anbindung des erzeugten Moduls an den Kern, die
Rust-Ports, die Adapter auf `embedded-hal` und `embedded-io`, der Ring
für Stream-Treiber, die Senken, die Testhilfe. `takt-embed-c`: das
SDK-Archiv je Ziel mit der C-Schnittstelle zum Kern; die C-Ports unter
`ports/` (Interruptform, Pollform, Zephyr, FreeRTOS, ESP-IDF,
CMSIS-RTOS2, POSIX) und die Vorlage `c-port`. Beide brauchen `unsafe`
für die Grenze zu C und stehen darum wie die Bring-ups außerhalb des
Workspaces (13.4).

### takt-mcu-program, takt-driver-probe, Treiber-Crates

`takt-mcu-program` geht im erzeugten Modul auf. Das Prüfgerät und die
Treiber-Crates aus M10 Schritt 11c erfüllen den Trait `Drivers`; das
Prüfgerät liest den Tick über den Wirtszeiger statt über
`takt_mcu_current_tick()`, das der Rahmen heute global exportiert.

### Bring-ups: takt-bringup-stm32f401, takt-bringup-esp32c6, takt-bringup-host

Bauskripte über `takt-embed`; `takt_state.x` wird zum Abschnitt der
Arena, `rwtext_hook.x` zum erzeugten Fragment; das Messprogramm über den
Bausteinweg.

### takt-conformance

Testtreiber (Stimulus) und Dump-Senke statt eines eigenen Wirtsrahmens;
das Differential über den Produktrahmen; ein Test für die Reentranz der
geteilten Bibliotheken; die Board-Suiten fahren die Portprüfung für jeden
mitgelieferten Port.

### examples, tools/cmake, Zephyr-Modul, ESP-IDF-Komponente

`examples/` mit einem Projekt je Form und Port (eigene Workspaces), die
zugleich die Vorlagen von `takt new` sind, und `examples/README.md` als
Anleitung für fremde Projekte; `tools/cmake/Takt.cmake` als CMake-Paket;
das Zephyr-Modul (`zephyr/module.yml`, `Kconfig`, CMake) und die
ESP-IDF-Komponente (`idf_component.yml`).

### Referenz und Register

Abschnitt 7; die neuen Zeilen in `plan/features.csv`; `plan/cert.md`
(TCB der Einbettung, die neuen Crates).

## 6. Risiken

| Risiko | Folge | Gegenmittel |
|---|---|---|
| Der Arena-Zeiger kostet doch Zeit | Klassengewichte oder `T_IO` steigen | Schritt 3 misst vor dem Weitergehen; steigt ein Gewicht um mehr als 5 %, wird die Ursache im IR gesucht, bevor Schritt 4 beginnt |
| Das Ende der schwachen Symbole zieht durch alle Rahmen und Tests | großer Umbau in einem Schritt | Schritt 5 allein, Stummel erzeugt statt von Hand |
| Das Zusammenlegen der Rahmen ändert das Wirtsdifferential | Abweichungen, die nicht am Codegen liegen | Schritt 9 erst nach festem Produktrahmen; beide Wege laufen über den ganzen Korpus nebeneinander, bevor `harness.rs` seinen Rahmen verliert |
| Bibliothek aus `clang`, Firmware aus GCC (Zephyr-SDK, ESP-IDF, ARM-GCC) | Link-Warnungen über ABI-Attribute oder stille Abweichungen bei Enums und Polsterung | Schnittstelle nur aus Typen fester Breite (2.7); je Port ein Link mit der GCC des Ports in der Portprüfung |
| ESP-IDF ist eine Beta (v6.1-beta1) | Schnittstellen ändern sich bis zur Freigabe | Version im Beispiel festschreiben; auf die Freigabe 6.1 heben, sobald sie erscheint |
| Zephyr und sein SDK sind groß | Installation und Bauzeit | Werkzeuge auf D: (HDD), Bauordner auf G:, `west` mit festem Manifest und nur vier Modulen; die Zephyr-Beispiele außerhalb der Pflicht-Suite, die Portprüfung auf Abruf |
